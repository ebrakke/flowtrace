FlowTrace Neovim tree UX explorations

The current tree is useful, but large traces can bury lineage between wrapped summaries, metadata rows, and deep indentation. These mock screenshots explore incremental ways to make “where am I and how did I get here?” obvious without abandoning a terminal-native Neovim workflow.

baseline

0. Current baseline

Represents the existing mental model: a persistent side tree with a jumpable location row plus label, metadata, and summary rows for every node.

Pros

  • Very explicit: every node carries its summary inline.
  • Simple implementation and familiar file-tree affordances.
  • Works well for short and medium traces.

Cons

  • Lineage gets separated by annotation rows.
  • Deep branches consume vertical space quickly.
  • Branches and repeated nodes do not pop strongly enough.
orientation layer

1. Sticky breadcrumb + active lineage

Add a sticky path line based on cursor position, then dim unrelated rows while highlighting ancestors and the current node.

Pros

  • Directly answers “what path am I on?” even after scrolling.
  • Can be layered onto the current tree renderer.
  • Low cognitive overhead; works like IDE breadcrumbs.

Cons

  • Long paths need truncation rules.
  • Highlight contrast depends on colorscheme.
  • Still leaves dense metadata in the main tree.
density

2. Compact rows + selected detail pane

Make each node a one-line row, then show the selected node’s full metadata and summary in a footer or floating detail pane.

Pros

  • More lineage fits on screen at once.
  • Preserves rich details without repeating them everywhere.
  • Nice default for large traces; details remain one glance away.

Cons

  • Less prose visible while scanning.
  • Requires a selected-node stateful render path.
  • Footer consumes fixed vertical space.
declutter command

3. Focus / show-my-path mode

A toggle that hides distant branches and keeps ancestors, the selected node, siblings, and immediate children.

Pros

  • Best for huge traces where the expanded tree becomes noise.
  • Maintains enough sibling context for local navigation.
  • Could be implemented as a render filter, not schema change.

Cons

  • Users need a clear indicator that content is hidden.
  • May feel surprising if it mutates expansion state.
  • Less useful when the goal is global overview.
visual grammar

4. Scope rails + branch badges

Replace some ASCII tree noise with persistent colored rails and make decision points explicit with compact badges.

Pros

  • Reinforces depth across wrapped or visually busy rows.
  • Branches become semantically distinct from plain children.
  • Still feels terminal-native and incremental.

Cons

  • Relies on highlight groups and terminal color support.
  • Deep nesting can still overflow horizontally.
  • Badges are only as good as branch labels in the artifact.
overview

5. Depth gutter + minimap

Add path/depth numbers on rows plus a tiny right-side overview showing viewport, depth changes, and active lineage.

Pros

  • Great for very large traces where scroll position matters.
  • Depth numbers are searchable and easy to reference in chat.
  • Minimap gives a quick sense of remaining tree shape.

Cons

  • Most complex concept to implement cleanly.
  • Consumes horizontal space in an already split UI.
  • Can become visual noise if always enabled.

Suggested path

First ship:
Breadcrumb + active lineage. It solves the core complaint with the smallest layout change.
Second:
Compact mode + detail pane as an opt-in for large traces.
Power-user:
Focus mode for “I am lost, show me only this path.”

Rails/badges are a good visual polish pass that can ride along with any of the above. The minimap is likely worth prototyping last, or only as a toggle, because it has the highest complexity-to-risk ratio.
